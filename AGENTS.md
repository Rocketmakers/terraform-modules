## What this repository is

Rocketmakers' shared Terraform modules: self-hosted CI runners (GitLab and GitHub, static and
autoscaling) on AWS, Azure and GCP, plus two `shared/` modules that build the shell commands used to
provision GitLab runners. Downstream projects consume a module by pinning a **git tag** in the module
`source`, so every tag is a contract. A change that would force a consumer to edit their code, or
would replace their running infrastructure on the next `terraform apply`, is a breaking change (see
[Releases and versioning](#releases-and-versioning)).

Read these first; they are the house rules and are not repeated here:

- [`README.md`](README.md): what makes a good shared module (no hard-coded values, lower-bound-only
  version constraints, no deprecation warnings at release, tests for every supported version).
- [`CONTRIBUTING.md`](CONTRIBUTING.md): tool setup, running validation and tests, documentation,
  branching and the release process.
- Each module's `README.md`: **generated**, see [Module READMEs are generated](#module-readmes-are-generated).
- [`.claude/skills/pr-review-response/SKILL.md`](.claude/skills/pr-review-response/SKILL.md):
  how to respond to pull request review threads in this repository, including the commit
  message contract. Its "commit contract" and "If it fails" sections apply to any commit here, not
  only review responses.

## Rules that the tooling enforces

These come from `README.md` and `CONTRIBUTING.md`; this is what actually checks them.

- **`terraform validate` warnings fail the build.** `_build/run/validate/validate.ts` treats
  `warning_count > 0` as a failure, so a deprecation warning from a provider upgrade is a red PR.
- **Formatting is checked, not fixed, in CI.** `pnpm format` is `terraform fmt -recursive -check`
  over the whole repository, including `_tests/config`. `pnpm format-fix` rewrites.
- **Module READMEs must match the code.** The Docs CI job regenerates them and fails on any diff.
- **Commit messages are conventional commits with a fixed scope list.** `commitizen` with
  `cz-customizable` (`allowCustomScopes: false`, `upperCaseSubject: true`) and
  `commit-and-tag-version` for the changelog. Types and scopes live in `.commit-config.js`.
- **Provider and Terraform constraints are lower bounds only** (`>= x.y.z`). One module currently
  breaks this; see [Known discrepancies](#known-discrepancies).
- **Test fixtures do not pin provider versions.** `_tests/config/**/backend.tf` declares
  `required_providers` with `source` only, and every test deletes `.terraform.lock.hcl` before
  `init` so providers float to the newest allowed by the module. One fixture currently breaks this;
  see `_tests/AGENTS.md`.

## Local commands

Everything runs through turbo from the repository root. `--filter @repo/typescript-scripts-core` is
optional because it is the only workspace package with these tasks; `CONTRIBUTING.md` includes it,
the skill omits it, both work. Script arguments go after `--`.

```bash
asdf install && pnpm install                                   # tools from .tool-versions, node deps (husky installs unless CI is set)

pnpm turbo validate                                            # terraform init + validate -json for every module (~1 min, needs network)
pnpm turbo validate -- --directory=gcp                         # one parent directory only (aws | azure | gcp | shared)
pnpm format                                                    # terraform fmt -recursive -check (exit 3 on unformatted files)
pnpm format-fix                                                # terraform fmt -recursive
pnpm turbo generate-docs && git status --porcelain             # regenerate module READMEs; anything listed must be committed

TERRATEST_DIR=gcp/gitlab-ci pnpm turbo terratest               # one terratest package; creates real cloud resources (see _tests/AGENTS.md)

pnpm cz                                                        # interactive conventional commit (also runs from the prepare-commit-msg hook)
HUSKY=0 git commit -m "fix(gcp-gitlab-ci): Subject"            # non-interactive commit; without HUSKY=0 the hook grabs /dev/tty
```

Every turbo task first runs `setup-dependencies`, which calls `asdf plugin add` and `asdf install`
for terraform, terraform-docs and github-cli with `|| true`, so it is safe when they are already
installed. All tasks are `cache: false` and `envMode` is `loose`, so environment variables such as
`TERRATEST_DIR`, `GITLAB_TOKEN` and `LOG_LEVEL` pass straight through.

Validation leaves `<cloud>/<module>/.terraform/` directories behind (gitignored). It also writes a
temporary `providers.tf` into each `aws/` and `azure/` module during the run and deletes it after;
never commit one (they are gitignored too). See `_build/AGENTS.md`.

## What CI checks

Defined in `.github/workflows/`. The composite action `.github/actions/setup` installs the
`.tool-versions` tools with `asdf-vm/actions/install@v4` and runs `pnpm install --frozen-lockfile`.

| Workflow | Trigger | Jobs |
| --- | --- | --- |
| `pull_request.yml` | every pull request, **except** branches named `release/*` | `Validate`: `pnpm turbo validate && pnpm format`. `Docs`: `pnpm turbo generate-docs` then `git diff HEAD --exit-code` |
| `main.yml` | push to `main` | the same two jobs |
| `create_tag.yml` | a PR from a `release/*` branch is merged into `main` (`pull_request_target: closed`) | checks `package.json` version is `x.y.z` and the branch is `release/<that version>`, then pushes annotated tag `v<version>` using the `REPO_COMMIT_KEY` deploy key so the push triggers `tag.yml` |
| `tag.yml` | any tag push | `gh release create` with notes linking `CHANGELOG.md`, then a Slack message via `SLACK_WEBHOOK_URL_PLATFORM` |
| `pull_request_reminder.yml` | weekdays 10:00 UTC and manual | Slack reminder of open non-draft PRs via `SLACK_WEBHOOK_URL_PR_REMINDERS` |

Things CI does **not** do:

- **Terratest never runs in CI.** The old GitLab pipeline ran the Azure and GCP GitLab-runner tests
  on `develop`; that was removed with the move to GitHub (commit `36492b0`). Tests are run by hand
  from a developer machine. There is no automated check that a module still applies.
- No cross-version matrix: validation uses the single Terraform version in `.tool-versions` and the
  newest providers allowed by each module's lower bound.
- `main` had no branch protection when this was written (September 2026); the release flow relies on
  convention, not enforcement.
- Copilot code review runs on pull requests in this repository (visible in the Actions history).
  Treat its comments like any reviewer's; the pr-review-response skill covers this.

## Module READMEs are generated

`<module>/README.md` is produced by `pnpm turbo generate-docs`
(`_build/run/readmes.ts` -> `_build/run/readme/readme.ts`):

1. `terraform-docs json ./` is run in the module directory.
2. Inputs are split into required and optional, sorted by name, and rendered through the root
   `readme.core.tpl` into the Required Inputs / Optional Inputs / Outputs / Requirements / Providers tables.
3. The module's own `readme.tpl` is rendered with `{{{ this.coreContent }}}` (those tables) and
   `{{{ this.version }}}` (the version from the root `package.json`).

So:

- **Never edit `<module>/README.md` by hand.** Change the variable or output `description`, or
  `readme.tpl`, then regenerate and commit the README in the same commit. This is why feature commits
  in the history touch `README.md` files as well as `.tf` files.
- The `?ref=v<version>` in every README example only changes during `release-prepare`; a feature PR
  regenerates with the current released version and produces no version diff.
- Descriptions are Markdown table cells: newlines become `<br />`, pipes are not escaped. Default
  values are JSON-stringified with surrounding quotes stripped (`"0 4 * * *"` renders as `0 4 * * *`).
- Any directory anywhere under the root that contains a `readme.tpl` is treated as a module for docs
  purposes. Do not add a `readme.tpl` to a fixture or test directory.
- The two `shared/` modules have no `versions.tf`, so their READMEs have no Requirements or
  Providers tables. That is expected.

## Releases and versioning

The process is in [`CONTRIBUTING.md`](CONTRIBUTING.md#release-process); the mechanics are in
`_build/AGENTS.md`. Summary: `release-prepare -- --as=major|minor|patch` on a clean checkout bumps
`package.json`, regenerates `CHANGELOG.md` and every README, and creates `release/<version>`;
`release-finalise` commits (`release: Changelog for v<version>`), pushes and opens a PR to `main`;
merging that PR creates the tag, the GitHub release and the Slack notification. The bump size is
chosen by the person releasing, not derived from the commits.

Versions are repository-wide. One tag covers all modules, so a breaking change in one module makes
the whole release a major.

**Breaking for consumers** (needs a `BREAKING CHANGE:` footer on the commit, which cz-customizable
prompts for, and a major release). All of these have happened in this repository's history:

- Renaming or removing a variable or output. `gcp/scalable-gitlab-ci/outputs.tf` shows the
  alternative: keep the old output with `[Deprecated]` in its description.
- Adding a variable without a default, or changing a default so that an existing deployment shows a
  plan diff (image, disk type, encryption, network policies, TLS settings).
- Raising `required_version` or a provider lower bound (v3.0.0: azurerm 2.97 -> 4.9, azuread 2 -> 3;
  the current branch raises azurerm to 5.0).
- Changing a resource type or address so Terraform must replace it (v2.0.0:
  `azurerm_virtual_machine` -> `azurerm_linux_virtual_machine` rebuilt every runner).
- Changing the provisioning script in `azure/scalable-github-ci` or `gcp/scalable-github-ci`: both
  hash the script into a replace trigger, so **any** edit, including bumping
  `github_runner_version`, recreates the whole scale set or instance group on the consumer's next
  apply. That is intended, and it is still a change the consumer must be told about.
- Changing anything in `shared/`: it is consumed by relative path, so it changes every GitLab runner
  module at once. See `shared/AGENTS.md` for why the change is often a silent no-op on existing VMs.

**Not breaking:** a new optional variable whose default preserves current behaviour, a new output,
documentation, tests, tooling. When a provider major version changes a default, the established
pattern is to expose the setting as a variable and say in its description which value keeps
existing infrastructure unchanged (see the three `azurerm 3.x` variables in
`azure/scalable-github-ci/variables.tf`).

### Commit types and scopes

From `.commit-config.js`. The subject line becomes the changelog line verbatim (type, scope and
subject; the body is dropped), so write it for someone reading release notes.

| Type | In changelog as | Use for |
| --- | --- | --- |
| `feat` | Features | new inputs, outputs, resources, behaviour |
| `fix` | Bug Fixes | corrections consumers should pick up |
| `upgrade` | Upgrades | provider, tool and dependency version bumps |
| `perf`, `refactor`, `test`, `build`, `ci`, `chore` | their own headings | as named; `chore` is "Other Changes" |
| `docs`, `style`, `release` | not in the changelog | docs-only (including everything under `.claude/` and these `AGENTS.md` files), formatting, release commits |

| Scope | Covers |
| --- | --- |
| `aws-gitlab-ci` | `aws/gitlab-ci` |
| `azure-gitlab-ci` | `azure/gitlab-ci`; historically also `azure/scalable-gitlab-ci` |
| `gcp-gitlab-ci` | `gcp/gitlab-ci`; historically also `gcp/scalable-gitlab-ci` |
| `azure-github-ci` | `azure/scalable-github-ci` (there is no non-scalable Azure GitHub module) |
| `gcp-github-ci` | `gcp/scalable-github-ci` |
| `shared-ci` | `shared/*` |
| `terratest` | `_tests/*` |
| `scripts` | `_build/*` |
| `config` | repository configuration (tool versions, commit config, CI definitions) |
| (none) | cross-cutting changes |

Scope names do not map one-to-one onto directories. Note the disagreement about the scalable GitLab
modules under [Known discrepancies](#known-discrepancies).

## Generated and vendored paths to ignore

All gitignored. Exclude them from searches or you will match vendored registry modules and stale
provider caches.

| Path | Origin |
| --- | --- |
| `node_modules/`, `_build/run/node_modules/`, `.turbo/` | pnpm and turbo |
| `<cloud>/<module>/.terraform/` | left behind by `pnpm turbo validate`; contains downloaded providers and, for GCP, vendored `terraform-google-modules` sources |
| `<cloud>/<module>/providers.tf` | temporary, written and deleted by validate (aws and azure only) |
| `**/.terraform.lock.hcl` | validate deletes the module ones; tests delete the fixture ones before every run |
| `_tests/config/**/.terraform/` | from running tests |
| `_tests/config/**/inputs.tfvars` | written by the tests (`rmutils.WriteTfvarsFile`) for debugging with the Terraform CLI. `terraform fmt -check` flags it, so `pnpm format` exits 3 locally while one exists. Delete it or ignore that line; CI never has one |
| `_tests/src/**/test_output.log`, `*.xml` | terratest log parser output on Linux |
| `*.tfplan`, `*.tfstate*`, `.DS_Store` | local artefacts |

`**/go.sum` is marked `linguist-generated` in `.gitattributes`.

## History that explains the odd bits

- The repository lived on GitLab (`gitlab.com/rocketmakers/infrastructure/terraform-modules`) with
  git-flow (`develop`, `release/*`, `master`), a `Makefile`, npm, `standard-version`, and a GitLab CI
  pipeline that ran the Azure and GCP GitLab-runner terratests. In September 2026 (commit `36492b0`)
  it moved to GitHub with trunk-based development on `main`, pnpm + turbo, `commit-and-tag-version`
  and GitHub Actions. `develop` and `master` still exist as branches and a `gitlab` remote may still
  be configured locally; `main` is the trunk. Old changelog entries link to gitlab.com; new ones will
  link to GitHub because `commit-and-tag-version` reads `repository.url` from `package.json`.
- Old `make` targets map to turbo tasks: `make validate` -> `pnpm turbo validate`,
  `make generate-docs` -> `pnpm turbo generate-docs`, `make test TERRATEST_DIR=...` ->
  `TERRATEST_DIR=... pnpm turbo terratest`, `make format-all` -> `pnpm format-fix`,
  `make bump-version` / `make changelog` -> `pnpm turbo release-prepare -- --as=...`.
- The GCP static runner module was once called `ci-box`; the name survives in the root `README.md`
  example, in module resource names (`google_compute_instance.ci_box`) and in prose in the GCP READMEs.
